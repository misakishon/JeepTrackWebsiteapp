# PUJ mobile UI implementation

The Driver and Passenger reference boards in the project root define the design direction: warm gray backgrounds, white bordered cards, navy headings, blue actions, semantic status labels, and compact fixed bottom navigation. The implementation uses React within the existing Laravel/Inertia application.

Entry points: /passenger/home, /driver/home, and /login. All requested secondary pages are linked from their parent destinations. Authentication forms are previews only; they never create accounts or change passwords. Driver preview access is explicitly a demo and does not grant an account role.

No database was added. Laravel uses file sessions for this UI prototype. Demo interactions persist in browser localStorage under `puj-ui`; timestamps use ISO strings and display in Asia/Manila. Demo controls let reviewers switch roles, clear local state, and inspect loading, empty, error, permission, and GPS states.

Mapbox GL JS is loaded on map screens from the official CDN. Set VITE_MAPBOX_ACCESS_TOKEN in .env, then rebuild Vite assets. The supplied public token is configured locally. Mapbox supplies real base-map tiles; route lines and vehicle markers remain explicitly illustrative, with no live tracking or ETA claims. Approximate route geometry is not turn-by-turn routing. Loading, connection failure, retry, a clearly labeled illustrative fallback, and Mapbox attribution are included. The browser location control asks for permission only when used.

Typography requests Inter and Google Material Symbols through Google Fonts. Inline Material-style SVG icons and system sans-serif keep the UI readable without network access. Mobile layouts use 16px page gutters, single-column cards, safe-area bottom padding, large form inputs, keyboard-friendly scrolling, and visible focus states. Wider screens retain a comfortable app column and a quiet brand panel.

Core safeguards: duplicate active passenger journeys are rejected, feedback submissions are idempotent per demo journey, manual alighting cannot exceed boarding, above-capacity counts are flagged, count corrections are retained, delays preserve active trips, and ending a trip never manufactures alighting records. Unsaved forms, journey corrections, ending trips, and logout have confirmation dialogs. Counts from app-linked records remain unavailable rather than being reported as zero.

Validation: production Vite build; 36 direct route renders with browser runtime checks; passenger boarding/arrival flow; driver start and nonnegative count guard; 390px overflow check. Mapbox's live CDN, token acceptance, and tile rendering cannot be verified in this environment because external DNS/network access is unavailable. The offline path is exercised explicitly. This is a UI prototype; server-side authorization, real GPS, emails, push notifications, and persistence services are intentionally not connected.

## Admin Analytics and Reports

Entry points: /admin/analytics, /admin/analytics/routes, /admin/analytics/passengers, /admin/analytics/drivers, /admin/analytics/vehicles, /admin/analytics/feedback, and /admin/reports. The admin reference image informs the desktop navy sidebar, blue actions, bordered white panels, and responsive two-column charts. At tablet/phone sizes the sidebar becomes a drawer and wide tables scroll within their own containers.

The implementation is in AdminAnalytics.jsx, admin.css, and the shared resources/js/admin modules. Deterministic fixtures provide completed/cancelled trips, reconciled boarding records, driver and vehicle assignments, GPS coverage, and feedback. All pages use the same metric engine and selected date/route filters. Secondary filters apply only to the relevant page; hidden filters do not silently constrain other pages. No database, passenger contacts, live telemetry, server roles, or external messaging were added.

Charts support accessible point/bar tooltips and legends. Tables have search, sortable columns, and pagination. Route, driver, vehicle, stop, trip, and feedback details open in drawers. Feedback edits and configurable delay thresholds persist in browser localStorage. Replies and internal notes remain visibly separated, and aggregate exports omit internal notes. Other sidebar destinations open read-only contextual demo directories, the sample tracking map, and local analytics settings.

Reports Center supports all six report types, date/route/driver/vehicle configuration, grouping, chart inclusion, and an explicit preview. PDF and CSV exports are real browser-generated files, not success-message placeholders. PDFs include headings, filters, metric summaries, vector charts, paginated tables with repeated headers, definitions, timestamps, and reporting timezone. CSV files include all matching detailed table records across pagination. Export progress, failure/retry, and no-record disabling are implemented. Fonts fall back to system sans-serif and inline Material-style SVGs when Google Fonts cannot load.

Validation: production build; seven analytics/reports routes and nine contextual sidebar destinations; route filtering and drill-down; detail drawers; driver duration safeguards; search; local feedback updates; six report previews; actual CSV/PDF downloads; disabled empty exports; responsive checks at 390, 768, 1280, and 1440px. Built-in Node tests in tests/ui/analytics-data.test.mjs verify reconciliation, distinct passenger counts, route/direction filtering, valid timestamp durations, equivalent comparison periods, missing denominators, CSV field isolation, and PDF pagination/cross-reference offsets.

Final admin checks also cover sidebar collapse/expand, table pagination and sorting, export failure feedback, connection retry, and disabled exports after an empty search. Report grouping partitions detailed results into daily/weekly/monthly buckets and applies per-bucket vehicle-time denominators. Seven metric/export tests pass, and the browser checks reported no runtime errors or viewport overflow. The login page now links the clearly labeled Admin analytics preview; leaving the admin workspace returns to the actual login application.

## MySQL integration

The former UI-only mode is now optional. The local `.env` enables TRANSPORT_DATABASE_ENABLED and connects to the existing PUJ MySQL database. The supplied Connector/J JAR is used by `transport:import --check` and the guarded empty-database import workflow; Laravel runtime queries use PDO_MYSQL. See MYSQL_SETUP.md for setup, schema coverage, account roles, timestamp handling, and verification commands. The original SQL and JAR are preserved.

Connected Admin pages replace generated fixtures with MySQL records and expose unavailable metrics explicitly. Login, passenger registration, logout, own-profile updates, and password changes use backend endpoints. Driver and Passenger connected views load role-scoped records rather than local demo records; unsupported journey/tracking/delay operations are unavailable until their backing schema exists. Existing account plaintext passwords are upgraded only after successful authentication. Database account credentials are not application sign-in credentials.

## Navigation and maps restored

Connected mode now keeps the original mobile app shell: logo, compact header, icon-based bottom navigation, blue cards, tracking sheets, and the desktop brand panel. Driver destinations remain Home, Trips, Tracking, Profile; Passenger destinations remain Home, Routes, My Trip, History, Profile. Client-side navigation preserves the app's filter state and scroll positions. Detail pages, forms, back actions, and unsaved-change confirmations remain available.

Mapbox maps are present in Driver trip details and tracking; Passenger route details, vehicle tracking, and My Trip; and Admin tracking and route details. Connected maps use stored Stops coordinates and actual latest GPS records. Missing route geometry is not replaced with a made-up route line, and missing GPS never creates a demo vehicle marker. Maps remain visible even without GPS. A labeled coordinate preview with stop selection, zoom, and recenter handles Mapbox connection failures.

Driver GPS reads are limited to vehicles on that driver's assigned trips. Passenger maps use public vehicle/route information without driver account data. Existing MySQL authentication, profile/password persistence, and role restrictions remain active. Seven PHP tests (36 assertions), the build, and browser checks across 32 mobile screens plus Admin tracking passed. Map SDK configuration was checked with a browser stub for stored coordinates, controls, attribution, and missing-GPS behavior; external tile rendering is not claimed as verified in this environment.

## Live trip GPS

Start Trip now commits the assigned trip's In Progress status and first valid GPS point to MySQL. Trip_GPS_Points associates fixes with the trip, vehicle, and driver using UTC capture/receipt times and idempotent client IDs. New timing columns preserve scheduled departure alongside actual departure/arrival. Drivers share GPS about every five seconds while the browser is visible, and passenger home/routes/tracking refresh every three seconds. Markers update without rebuilding Mapbox. Stale locations, accuracy, permission errors, HTTPS requirements, and connection loss are visible. End Trip records completion and stops sharing without fabricating alighting. The original navigation and layout remain. See MYSQL_SETUP.md for phone requirements and validation limits.

Analytics implementation update: preserved the current desktop and mobile layouts. Removed hard-coded disabled analytics charts and connected Refresh to MySQL. Added shared persisted metric threshold, per-day vehicle availability and upcoming schedules; added operational journey, delay and feedback recording to supply the charts. Legacy missing observations remain explicitly unavailable or excluded with coverage notes. PDF/CSV use current filters, source, coverage and sample sizes. Validated all seven pages in a desktop browser and the drawer navigation at 390px.

## Driver account creation

Admin > Drivers now uses the existing Panel, Button and DataTable primitives for an account directory and an inline Add driver form. It lists all driver accounts independently of analytics dates or completed trips. The form accepts name, sign-in email, unique license number, password and confirmation; validation errors are inline, keyboard focus enters the form and returns to Add driver on close, and fields stack on mobile. Public registration stays passenger-only and explains where driver accounts are created. No schema migration or new dependency is required.

The admin-only GET/POST `/api/admin/drivers` endpoints list safe fields and create a hashed User plus linked Driver inside one transaction without replacing the administrator's login session. A driver account does not automatically create vehicle/trip assignments. Verified with backend authorization/validation/login tests and an isolated MySQL browser run including 1440px, 768px and 390px layouts, search, validation, creation, admin session retention and the new driver's login.
